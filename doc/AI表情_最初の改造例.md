# AIが会話に合わせて表情を選ぶ

## 今回の公開時点（2026年11月18日）

ブランチ `sample/ai-gestures` を、**AIが表情を2択から選ぶ機能を実装し、実機で最初の3往復を確認した段階**の改造例として公開します。
学生の皆さんが、関数呼び出しを通じてAIの選択を本体の表情へつなぐ仕組みを読み、試し、次の改造を考えるための出発点です。

| 項目 | この公開時点の状態 |
|---|---|
| AIが選べる表情 | 笑顔（happy）と通常（neutral）の2種類 |
| ビルド・書き込み | CoreS3・Core2向けビルド成功。CoreS3実機への書き込みと起動を確認 |
| 実機で確認した会話 | 「笑顔にして」→「普通の顔に戻して」→「試験に合格したよ」の3往復。同じ接続で音声返答と表情変更が続いた |
| 返答後の動作 | 録音が再開し、通常の顔へ戻ることを確認 |
| 声と表情のタイミング | 表情が声より先に変わる場合と、声が始まってから変わる場合があった。厳密な同期は未対応 |
| 音質 | 聴感では気になる途切れなし。ただし初回にバッファの途切れ検出が1回あり |
| AIによる首の動作 | 未実装。うなずきの追加は次の段階。従来の会話状態に応じた首の動きは残っている |

確認したのは上記の短い会話です。長時間・多様な会話での安定性、切断・エラー時の表示と復帰、複数の関数要求や不正な引数の実行時試験は、これから確認する課題です。Core2はビルドのみで、実機動作は確認していません。
AIの表情選択には揺らぎがあり、同じ言葉で毎回同じ表情になることや、毎回声より先に表情が変わることは保証しません。
詳しい実測結果は後述の「初回の実機結果」に記載しています。

## この改造で示すこと

Geminiに「笑顔（happy）」「通常の顔（neutral）」という2つの選択肢を渡します。
会話に合う表情をAIが選び、本体が画面へ反映します。音声の入出力は引き続きGemini Liveを使います。
首のうなずきは次の段階です。

このリポジトリには、もともと6種類の表情を選ぶ関数がありました。
今回の改造は、それを教材として2種類に絞り、既存の自動表情と競合しないようにするものです。
従来の「AIが話すと必ず笑顔になる」表示と、AIが会話を考えて選んだ表情は区別します。

## 関数呼び出しの流れ

1. 本体が接続時に `set_avatar_expression` という関数と2つの選択肢をGeminiへ知らせます。
2. Geminiが会話内容に合わせて、例えば `{"expression":"happy"}` を返します。
3. 本体が関数名と引数を確認し、表情の選択を記憶します。
4. 画面を更新する処理がその選択を反映します。
5. 本体が呼び出しid付きの結果をGeminiへ返します。Geminiは音声の返答を続けます。

AIからプログラムそのものを受け取って実行する仕組みではありません。
用意した関数と、許可した引数だけを受け付けます。

例：受信する要求のイメージ

```json
{"toolCall":{"functionCalls":[{
  "id":"example-1",
  "name":"set_avatar_expression",
  "args":{"expression":"happy"}
}]}}
```

返す結果のイメージ（画面への反映はUI処理が担当するため、結果は「選択を受け付けた」です）

```json
{"toolResponse":{"functionResponses":[{
  "id":"example-1",
  "name":"set_avatar_expression",
  "response":{"result":"expression selected","expression":"happy"}
}]}}
```

## コードを読む順番

- `firmware/src/llm/Gemini/GeminiLive.cpp` の接続処理：既存の関数定義を使い、選択肢を2つに絞る。
- 同ファイルの `load_role()`：どういう会話で表情を選ぶかをAIに伝える。
- 同ファイルの `handleToolCalls()`：引数を確かめ、選択を保存し、結果を返す。
- 同ファイルの `applyResponseExpression()`：保存した選択を顔の表示へ変換する。
- `firmware/src/mod/AiStackChan/RealtimeAiMod.cpp` の `idle()`：既定の表情よりAIの選択を優先する。エラー表示を最優先する。
- `firmware/src/llm/RealtimeLLMBase.cpp`：次の録音やエラー時に、前の選択を解除する。

表情の選択は受信タスクとUIタスクで共有するため、`std::atomic<int>` を使います。
これは、別々に動く2つの処理の間で、選択した値を安全に受け渡すためです。
元の `FunctionCall::set_avatar_expression()` は直接顔を変更するので、今回はその関数定義を再利用し、表示自体はUI側にまとめています。

## 声とのタイミング

AIには、できれば声の返答の前に表情を選ぶよう指示します。
ただし、要求が届く順番は毎回同じとは限りません。表情は要求の受信後、次のUI更新で反映します。
声が先に届いた場合は、発話途中から表情が変わります。単語単位で同期する機能ではありません。
AIの選択がない間は従来の会話状態による表情を使います。
返答が終わって次の録音が始まると、表情を通常へ戻します。

## 本体での確認

2026-11-18に本体への書き込み、起動、Wi-Fi接続、表情2択の登録、Geminiの接続完了と、同じ接続での3往復の音声会話・表情変更を確認しました。
テスト前に [AI Studioの使用状況](https://aistudio.google.com/app/usage)で無料枠を確認します。
無応答や切断が起きても、設定を変更する前に使用状況を確認します。課金は使いません。

変更はプログラムだけです。`data/` の変更と `uploadfs` は不要です。
COMポートを確認し、シリアルモニターを閉じてから、`firmware/` で実行します。
`COMx` は接続中の本体のポートに置き換えます。

```powershell
& "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe" run -e m5stack-cores3-realtime -t upload --upload-port COMx
```

| 確認 | 話しかける例・見るところ |
|---|---|
| 関数を確実に試す | 「笑顔にして」「普通の顔に戻して」 |
| 内容に応じた選択を見る | 「試験に合格したよ」「今日の予定を一緒に考えて」など、表情を指定せず話す |
| 本当にAIが選んだか | `[T ...] AI expression=happy/neutral id=... speaking=...` が出たか見る。既定の笑顔だけでは成功としない |
| 会話が続くか | 同じ接続で3往復以上。表情変更後も声が出て、次の話を聞くか |
| タイミング | 表情が声の前／途中で変わるか。発話開始でAIの選択が上書きされないか |
| 終了・エラー | 次の録音時に通常の顔へ戻るか。切断・無音時のエラー表示が優先されるか |
| 音の品質 | `[AUDIO] starve` と聴感を変更前と比較する |

AIの選択には揺らぎがあります。特定の文で毎回必ず同じ表情になるとは限りません。
ログは `AGENTS.md` の取得方法と秘密情報の除外フィルタを使います。

## 初回の実機結果（2026-11-18）

上記の3つの発話例の順でテストし、本体ログとユーザーの観察を照合しました。

| 返答 | AIの選択 | 表情の指示が届いたタイミング | 音声の途切れカウンタ |
|---|---|---|---|
| 1回目 | happy | 音声開始から約1.3秒後 | 1 |
| 2回目 | neutral | 音声開始前 | 0 |
| 3回目 | happy | 音声開始前 | 0 |

3回とも音声で返答し、表情も変化しました。各返答の終了後に録音が再開し、「きいてるよ」と通常の顔へ戻りました。
ログに切断・エラーはなく、ユーザーの聴感では気になる途切れもありませんでした。ただし1回目のカウンタは1なので、途切れを常にゼロにできたという結果ではありません。
切断・エラー時の表示、複数の関数要求や不正な引数の実行時試験、変更前との同条件の音質比較は未実施です。

書き込みが途中で止まった際は、底面リセットボタンを約3秒押して書き込みモードへ入り、再試行して成功しました。
書き込み後も画面が暗く、ログが `DOWNLOAD(USB/UART0)` の場合は、底面ボタンを短く1回押すと通常起動へ戻りました。

## 次に追加するなら

上の確認が済んだ後で、決められた小さな角度で1回だけうなずく動作を加えます。
最初は音声再生と重ならないタイミングで試し、既存のサーボタスクと競合しないようにします。
AIに首の角度を自由入力させる機能は、その後の課題です。
